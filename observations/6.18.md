# Observations: 6.18

Entries for the 6.18 state of the series. Reports of other people name
their system and kernel in the entry.

## 2026-11-19: KeinNiemand, bees with one metadata copy on NVMe

- Author: KeinNiemand
- Source: PR [#40][pr-40], [comment of 2026-11-19][c-report], with Kai
  Krakow's [reply][c-reply]

System of KeinNiemand: btrfs on four HDDs and one NVMe, metadata RAID1C3.
The btrfs series of PR [#40][pr-40] in its 6.18 state with the user's
early RAID1C3 variant. The fixed-width mirror patch "btrfs: honor
allocator hints for fixed-width mirrors" is part of the 7.3 series
(PR [#47][pr-47]). The report names no kernel. 7.0 is inferred from
context: the [comment of 2026-08-26][c-port] mentions the user's Ubuntu
HWE 7.0 port.

State: NVMe devid with allocator hint type 1 (`PREFERRED_METADATA`), the
HDDs type 0; metadata RAID1C3; read policy `queue-adaptive`. Compared
with the same pool before the NVMe was added (metadata only on HDDs).

Method: the `TOTAL` counters of the bees status file were read before and
after 600 s and subtracted. In addition, `btrfs_ioctl_logical_to_ino` was
traced for the bees PID in two samples of 120 s, added up to 240 s.

bees, 600 s:

| Counter | Before (HDDs only) | After (NVMe) | Factor |
|---|---:|---:|---:|
| `scanf_extent` completed | 185 | 5321 | 28.8x |
| `scanf_total` completed | 107 | 4190 | 39.2x |
| `extent_forward` | 130 | 4190 | 32.2x |
| `crawl_extent` | 0 (stalled) | 916 | active |
| `dedup_bytes` | 55,439,360 | 2,785,394,688 | 50.2x |
| Time per `scanf_extent` | 3.09 s | 0.222 s | |

`LOGICAL_INO`, 240 s:

| Value | Before (HDDs only) | After (NVMe) |
|---|---:|---:|
| Completed calls | 86 | 10174 (118.3x) |
| Calls per second | 0.358 | 42.39 |
| Mean latency | 2067 ms | 2.39 ms |
| Median latency | 128 to 256 ms | < 1 ms |
| p95 latency | 8 to 16 s | 4 to 8 ms |
| p99 latency | 32 to 64 s | 32 to 64 ms |
| I/O wait per call | 2045 ms | 1.65 ms |
| Metadata read BIOs | 14524 (60.5/s) | 129589 (540/s) |
| Target of metadata reads | HDDs | NVMe |

No metadata read BIO observed after the change went to an HDD.

- **What it shows:** mainly the allocator hints together with the
  fixed-width mirror selection, which put one of the three metadata copies
  on the NVMe. Metadata reads moved to that copy, and bees went from a
  stalled crawl to active deduplication.
- **queue-adaptive only indirectly:** zero metadata reads on the HDDs is
  consistent with the latency veto of `queue-adaptive` (the guard clamps
  a large latency ratio to 16), but there is no A/B comparison of `queue`
  against `queue-adaptive` on this layout. The report mentions
  measurements with and without `queue-adaptive`, but posts no separate
  numbers for them.
- **Caveats:** bees ran with `--throttle-factor 0.5` before and `0` after.
  The measurements are about two weeks apart (status files of 2026-08-18
  and 2026-08-31), the second one day after a finished rebalance. The
  links to raw data in the comment are broken (no files were uploaded).
  The counters were taken with a script of the user; the comparison and
  the summary in the report were written by an AI agent of the user.
  Metadata writes still go to the HDD copies as well.
- **Open:** the raw data; the separate numbers with and without
  `queue-adaptive` the report mentions (to be asked for); an A/B run of
  `queue` against `queue-adaptive` on the same layout with `read_stats`
  (vetoed and overflow per devid), as a data basis for a possible
  `queue-adaptive` RFC.
